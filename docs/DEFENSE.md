# Пакет к защите дипломного проекта «ЧекСкан»

Всё ниже — заготовки: тексты для слайдов, сценарий демо, ответы на вопросы.
Команда может править формулировки под себя, но фактура (цифры, архитектура) уже проверена.

---

## 1. Структура презентации (12 слайдов)

1. **Титульный.** «ЧекСкан — мобильное приложение учёта расходов по фото чеков». Авторы, группа, руководитель.
2. **Проблема.** Чеки копятся и теряются; ручной учёт в заметках/Excel утомляет → расходы не контролируются. Целевая аудитория: студенты, молодые семьи, фрилансеры.
3. **Аналоги.** Дзен-мани, CoinKeeper, Money Manager. Минусы: ручной ввод каждой покупки, платная OCR, нет белорусского контекста. Наше отличие: фото → сумма за секунды, свободный стек, лимит бюджета.
4. **Функциональные требования.** Регистрация/вход, съёмка чека, OCR + экран корректировки, ручной ввод, история с деталями, статистика (неделя/месяц/всё), категоризация, лимит месячного бюджета, профиль (тема, уведомления).
5. **Архитектура.** Схема: React Native (Expo) ↔ HTTPS/JSON ↔ FastAPI ↔ Tesseract OCR + парсер; PostgreSQL; JWT + bcrypt. Подписать: чистое разделение — клиент не знает про OCR, сервер не знает про UI.
6. **OCR-пайплайн.** Фото → предобработка (поворот OSD, два прохода бинаризации) → Tesseract rus+eng → парсер (регулярки: ключевые слова ИТОГО/ИТОГ/VAT-ловушка, последняя помеченная сумма) → категоризация по словарю магазинов/ключевых слов.
7. **Метрики качества.** По 7 пригодным чекам из 9: сумма 6/7 (86%), дата 5/7 (71%), категория 5/7 (71%). Порог по сумме ≥ 70% перевыполнен; дата близка. Экран корректировки (3–5 с руками) покрывает остаток — заявленный UX. Источник: docs/OCR_ACCURACY.md.
8. **База данных.** Диаграмма: users (профиль, бюджет, настройки), receipts (магазин, дата, сумма, категория, статус draft/confirmed, confidence), receipt_items. Связь 1:N. Статус-модель: draft → confirmed.
9. **Демо.** 3–4 скриншота ключевых экранов + QR на APK (см. сценарий ниже).
10. **Тестирование.** Backend: 25 unit/интеграционных тестов (pytest, SQLite in-memory). Сквозной сценарий на живом сервере с реальным фото чека (регистрация → скан → подтверждение → статистика). TypeScript-клиент проходит tsc без ошибок.
11. **Трудности и решения.** Поворот фото (OSD + word-count fallback); НДС/VAT, принятый за итог (исключение строк); скидка после промежуточной суммы (последняя помеченная, не максимум); разорванные цифры «4 199,00» (регулярки с допуском пробелов); рукописные счета — осознанное ограничение (ручной ввод).
12. **Перспективы.** Google/Apple OAuth, push-уведомления о превышении бюджета, экспорт в CSV/PDF, улучшение распознавания даты (английские месяцы, нейросетевой OCR как опция).

## 2. Демо-сценарий (5–7 минут)

**Подготовка (за день до защиты):**
- Деплой на Render поднят, в БД заведён демо-аккаунт `demo@checkscan.by / Demo2026!` с 10–15 чеками за текущий месяц (забить через экран ручного ввода — быстрее всего).
- На телефоне: APK установлен, залогинен демо-аккаунтом, 1 реальный чек сфотографирован заранее и лежит в галерее (страховка от плохого света/инета).
- Заранее открыть вкладку Swagger `https://…onrender.com/docs` — план Б.

| Время | Шаг | Что говорить |
|---|---|---|
| 0:00–0:30 | Главный экран | «Это баланс месяца, лимит 5000 Br и последние чеки — всё считается сервером» |
| 0:30–2:00 | Живой скан | Сфотографировать чек → «сервер распознаёт за 5–15 секунд: сумму, дату, магазин и категорию» → показать экран корректировки с подсвеченными полями |
| 2:00–2:30 | Корректировка | Поправить одно поле руками → «OCR не идеален — поэтому подтверждение всегда у пользователя» → сохранить |
| 2:30–3:30 | История | Открыть историю → bottom sheet с позициями → удалить черновик/лишний чек |
| 3:30–4:30 | Статистика | Переключить неделя/месяц/всё → график + категории → «лимит месяца использован на N%» |
| 4:30–5:00 | Профиль | Тёмная тема, лимит бюджета → «сервер сохраняет настройки» |
| 5:00–5:30 | Ручной ввод | «Чек не читается или рукописный — заполняем вручную за 20 секунд» |

**Офлайн-запасной план (если нет интернета/Render уснул):**
1. Демо-аккаунт уже залогинен, история/статистика подтянуты с сервера ранее → показать кэш.
2. Скан по заранее сохранённому фото → если сервер недоступен, перейти к Swagger/видеозаписи.
3. Запасной вариант — заранее записать 2-минутное видео демо и встроить в презентацию.

## 3. Вероятные вопросы комиссии и заготовки ответов

1. **Почему Tesseract, а не нейросеть?** Tesseract — зрелый open-source движок с поддержкой русского, не требует GPU и дообучения. На печатных чеках после предобработки даёт 86% точности суммы, что выше целевого порога 70%. Нейросетевой OCR (PaddleOCR, easyOCR) — в roadmap как апгрейд, но он тяжелее и требует данных для дообучения.
2. **Что с точностью распознавания?** Сумма 86%, дата 71% (7 реальных чеков, docs/OCR_ACCURACY.md). Ошибки не «молчаливые»: низкоуверенные поля подсвечиваются на экране корректировки, итог всегда подтверждает пользователь. Это сознательный UX: 3–5 секунд руками надёжнее, чем авто-сохранение ошибки.
3. **Почему в тестах SQLite, а в проде PostgreSQL?** SQLAlchemy даёт переносимость: тесты гоняются на SQLite in-memory (быстро, изолированно, без Docker), прод — PostgreSQL на Render. Типы данных и запросы выбраны совместимыми, CI это проверяет.
4. **Насколько безопасны данные?** Пароли — bcrypt (хэш, не обратимый). Сессии — JWT с секретом из переменной окружения. Чеки доступны только владельцу (проверка user_id на каждом запросе). Фото чеков хранятся на сервере, в репозиторий не коммитятся (в .gitignore).
5. **Как работает категоризация?** Двухуровневая эвристика: сначала словарь магазинов (DNS → Электроника, АЗС → Транспорт), затем ключевые слова по тексту чека. Точность 71%, категорию всегда можно сменить при подтверждении.
6. **Как отличить итоговую сумму от НДС и промежуточных итогов?** Парсер исключает строки с VAT/MwSt/НДС/%, берёт последнюю помеченную ключевым словом сумму (не максимум — иначе схлопываемся на скидках после промежуточного итога).
7. **Почему React Native / Expo, а не нативка или Flutter?** Одна кодовая база на iOS и Android, Expo ускоряет разработку (камера, secure-store из коробки), TypeScript снижает ошибки контракта с бэкендом. Критичных по производительности экранов нет.
8. **Что будет, если пользователь сфотографирует рукописный счёт?** Tesseract заточен под печатный текст. Рукописный чек распознается плохо — поэтому есть кнопка «Заполнить вручную», это заявленное ограничение (слайд 11).
9. **Как масштабироваться при росте пользователей?** Stateless FastAPI → реплики за балансировщиком; PostgreSQL → пул коннектов и индексы (уже есть по user_id/date); OCR — самая тяжёлая часть → вынос в очередь (Celery/RQ) с воркерами.
10. **Почему нет OAuth (Google/Apple)?** Реализация занимает 1–2 недели (регистрация приложений, review Apple/Google, хранение провайдерских токенов). Для MVP выбран классический email+JWT; OAuth — первый пункт перспектив.
11. **Кто что делал в команде?** *(вписать фамилии)* — бэкенд и OCR-пайплайн: ___; мобильное приложение: ___; дизайн и UX: ___; тестирование и метрики OCR: ___; DevOps (Render, EAS, CI): ___. Задачи закреплены в GitHub Issues репозитория.
12. **Сколько времени занял проект и что самое сложное?** *(оценить честно)*. Самое сложное — не код, а качество OCR на «грязных» реальных чеках: поворот, бледная термобумага, скидки после промежуточного итога. Решалось предобработкой и эвристиками парсера (слайд 11).

- [ ] ⚠️ Free-БД Render удаляется через 90 дней: назначить ответственного за перенос/продление, либо платный план (~$7/мес)

**Мобильное приложение (APK):**
- [ ] `cd mobile && npm install`

- [ ] Цель: добить дату до ≥ 80% (англ. месяцы, типичные бел. форматы даты)
